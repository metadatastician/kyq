= kyq
:toc:
:toclevels: 2

Native Rust processing for KYAML, strict I-JSON/JCS, import-free Dhall and a separate TOML 1.0 validity-only gate.

kyq validates structured data, queries it with JSON Pointer, formats KYAML,
and produces deterministic JSON bytes through
https://github.com/hyperpolymath/ijson-jcs[ijson-jcs].
https://github.com/hyperpolymath/docmatrix[DocMatrix] uses the same parsing boundary.

This is the Rust migration candidate. Earlier AffineScript sources remain
historical research. link:docs/ASSURANCE.adoc[The acceptance record] separates
executed checks from outstanding requirements for estate-wide adoption.

== Start

Install Rust/rustup and Git. The repository pins its Rust toolchain.
Bash is needed for the launcher and Just recipes; Windows users can use
Git Bash or WSL, or invoke Cargo directly.

[source,sh]
----
cargo build --locked --release
cargo run --locked -- --help
./launcher.sh --run validate examples/deployment.yaml
just check
----

Run `just` to discover build, test, benchmark, documentation, provisioning and
Podman tasks. link:docs/SETUP.adoc[Setup] covers manual installation, mise and Guix.

== Commands and formats

[source,sh]
----
kyq validate --from kyaml manifest.yaml
kyq validate --from toml configuration.toml
kyq canon --from json document.json
kyq to-json --from dhall configuration.dhall
kyq get --pointer /metadata/name manifest.yaml
kyq fmt manifest.yaml
kyq check manifest.yaml
kyq --capabilities
----

Omit the filename or use `-` to read stdin. Input format is explicit and
defaults to KYAML; a file extension does not establish content validity.

[cols="1,3",options="header"]
|===
|Operation |Contract
|`validate` |Parse and validate; no rewritten output. For TOML 1.0, this is the only supported operation, preserving the original file.
|`canon` |Exactly one document, RFC 8785 bytes without a final newline.
|`to-json` |Exactly one document, canonical bytes plus LF.
|`get` |RFC 6901 JSON Pointer, one result per document.
|`fmt` |Block KYAML on stdout; retains data and mapping order, discards comments.
|`check` |Compare with native formatted bytes; never modify input.
|===

Use +kyq --capabilities+ to inspect an installed binary's supported operations,
resource limits and known gaps without parsing a file. The JSON schema is a
preview, not yet a stable compatibility promise. See
link:docs/CAPABILITIES.adoc[executable capability contract].

Exit status is 0 for success, 1 for valid input with formatting drift, and
2 for invalid input or usage. See link:docs/NATIVE-MIGRATION.adoc[the native CLI boundary].

Duplicate keys are checked before map construction. Unsafe integer tokens,
non-finite numbers, unsupported YAML constructs and invalid UTF-8 are rejected.
Input is capped at 8 MiB, with explicit YAML depth and expansion budgets.
Dhall expressions are typechecked; local, environment and remote imports are
disabled. Untrusted Dhall evaluation still needs external process time and
memory limits.

TOML uses a dedicated TOML 1.0 parser: its datetime types, comments and original
bytes are not coerced into the JSON-shaped value model. The only TOML
operation is `validate --from toml`; `canon`, `to-json`, `get`, `fmt` and
`check` are explicitly refused (exit 2), with no file modification. See
link:docs/TOML_VALIDITY.adoc[the TOML validity contract].

JCS binary64 formatting and the estate's safe-integer-token policy are distinct.
Strict I-JSON and KYAML refuse floating-point numbers whose JCS representation
would be an integer token outside the safe-integer range (owner ruling R3).
Explicit +--from jcs+ retains RFC 8785 binary64 semantics for those values;
its output is not necessarily valid strict I-JSON. The native formatter also
refuses KYAML values outside the strict domain instead of silently emitting
non-reingestable text.

== Rust, Creusot, Pearlite and Verus

The production bounds function is Rust with a Pearlite postcondition verified
by Creusot. The parser uses it for resource accounting. A separate Verus model
checks the corresponding arithmetic property. See
link:verification/README.adoc[the precise proof boundary and executed receipts].

These obligations do not establish formal correctness of the complete parser,
YAML scanner, Dhall evaluator or JCS implementation. Full parser refinement
and the dependency trust boundaries remain explicit obligations.

Native tests check all 118 bridge vectors and all 49 committed KYAML fixtures,
including declared diagnostics. Property tests and adversarial inputs supply
additional empirical evidence.

== JSON ingress and JCS wire numbers

Use `--from json` (or `ijson`) for strict integer-token ingress: integer tokens
outside ±(2^53−1) are rejected. Use `--from jcs` to read RFC 8785's binary64
numeric model, including canonical output containing larger integral doubles.
For example, JSON input `1e16` canonicalizes to `10000000000000000`; read those
bytes with `--from jcs`. The explicit JCS reader rounds numeric tokens to
binary64, so `9007199254740993` becomes `9007199254740992`. Preserve identifiers
and arbitrary-precision values as strings. Duplicate keys, invalid Unicode,
non-finite values, trailing input and size limits remain errors in both modes.

In Rust, select `Format::Json` or `Format::Jcs` explicitly. `check --from jcs`
uses the estate-file byte profile: canonical JCS plus exactly one LF. `canon`
always emits library bytes without LF. These input policies do not change the
KYAML core schema or Dhall's type system.
