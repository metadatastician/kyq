== Accepted port deltas

The source changes were made in small commits, each followed by the same pinned
compiler census:

. Replaced `break`/`continue` with structured loop conditions and explicit
  `parsing`/`scanning` booleans. Run 40231554414 moved the first parser error
  from 23:12 to 124:67.
. Split binary minus from numeric literals (`len(t) - 1`, not `len(t)-1`).
  Without whitespace, v0.1.1 can lex `-1` as a negative literal. Run 40231646231
  moved the first error to 407:15.
. Replaced underscore-prefixed names such as `_v`/`_e` with the wildcard `_`.
. Replaced unresolved `to_string(i)` with `int_to_string(i)` and terminated an
  intermediate `match` statement with `;`.
. Converted character ordering checks to ASCII code-point comparisons with
  `char_to_int`; v0.1.1's ordering operators are numeric. Run 40231861263 reached
  record type checking.
. Kept the public AST records unchanged but added parser-internal structural
  aliases with identical layouts. This works around the imported-struct defect
  described below. Run 40232018985 is the passing result above.

== Imported-struct upstream defect

A same-module struct literal passes A1's `record_literal` probe. In the parser,
however, both `#{ ... }` and `ParseErrorDetail #{ ... }` produced:

[source,text]
----
Unification error: (Unify.TypeMismatch
  (ParseErrorDetail,
   {context: Option[String], column: Option[Int], line: Option[Int], message: String}))
----

The v0.1.1 resolver copies imported value schemes but not the imported struct
definitions into the importer's `type_env`. The importer therefore treats the
struct name as an opaque constructor while the literal has a record type. The
parser's private `ErrorDetail` and `Document` aliases retain exactly the public
AST layouts and unify with `ParseError`/`ParseSuccess`. This is a scoped local
workaround, not evidence that imported structs work upstream. The upstream
handoff prompt is in `docs/UPSTREAM_HANDOFFS.adoc`.

== Remaining limits

* A4–A8 remain open. The current six source failures are listed above.
* No `affinescript compile`, `affinescript test`, WASM invocation, or CLI run has
  been performed.
* The executable JavaScript conformance harness remains an oracle, not the
  AffineScript implementation or a substitute for it.
* The parser's duplicate-key `panic`, minimal scalar support, rejected document
  streams, and stub lexer still require semantic/conformance work; source-check
  acceptance does not make them spec-compliant.
* A7 still needs a released toolchain with demonstrated argv/stdin/stdout/
  stderr and exit-code behaviour. No PyYAML-removal claim is made.
