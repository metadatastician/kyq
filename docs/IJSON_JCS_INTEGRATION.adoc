== The estate JSON standard (D306)

The canonical estate reference is `hyperpolymath/ijson-jcs`:

* Repository: https://github.com/hyperpolymath/ijson-jcs
* Pinned oracle: commit `2c880594c8b1f823a7ab2a8a830c894975a1792e`
  ("Clarify kyq's four-format estate route and kyX boundary (#6)"),
  crate `ijson-jcs` 0.1.0, `edition = "2024"`, license MPL-2.0.
* Specs: I-JSON RFC 7493 (MUST + SHOULD) + JCS RFC 8785 (deterministic bytes).

`ijson-jcs` ships a Rust library (`src/*.rs`: `lib.rs`, `ijson.rs`, `jcs.rs`,
`strict.rs`, `error.rs`, `bin/*.rs`) and a CLI (`ijson-jcs check`/`fix`/`canon`).
This document does not re-specify JCS; it references `ijson-jcs` and pins it by
commit so the comparison is reproducible.

== What kyq must inherit exactly

=== 1. Validation mode

Every `kyq` entry point that touches JSON canonical bytes parses as strictly as
`ijson_jcs::JsonMode::Canonical`:

* UTF-8 input; a BOM is not accepted as whitespace.
* Duplicate object keys → `INVALID`, detected while reading the text (a parsed
  `Value` can no longer show them — `validate_i_json(&Value)` alone cannot).
* Integer tokens outside ±(2^53−1) → `INVALID`; float tokens are accepted as
  doubles; numbers outside the binary64 range (`1e400`) → `INVALID`.
* Strings/keys: no unpaired surrogates (`U+D800..U+DFFF`), no noncharacters;
  escaped control characters are allowed (RFC 7493 §2.1 does not forbid them).
* Top-level value: `ijson-jcs` follows RFC 7493's SHOULD here by *allowing* any
  value; `kyq` does the same, so the two agree.

Executable: `conformance/fixtures/ijson/vectors.json` (38 vectors),
`conformance/fixtures/oracle/ijson-jcs.json`, `conformance/test/json.test.js`.

=== 2. Canonical bytes (JCS)

For the same logical value, `kyq` produces byte-equal output to
`ijson_jcs::to_jcs` / `to_jcs_string`:

* UTF-8, no BOM.
* Object keys sorted by *UTF-16 code-unit* order (RFC 8785 §3.2.3), not by code
  point and not lexicographically.
* No insignificant whitespace; arrays keep their order.
* Numbers serialised per ECMAScript `Number.prototype.toString`
  (`1E30`→`1e+30`, `4.50`→`4.5`, `-0`→`0`, `1e-7`→`1e-7`,
  `1e+20`→`100000000000000000000`).
* Strings escaped as `serde_json` does: only `"`, `\` and C0 controls, the short
  forms where they exist, `\u00xx` lowercase hex otherwise; `/` and all
  non-ASCII stay raw.
* Determinism and idempotence: same input, same bytes.

Executable: `fixtures/rfc8785/vectors.json` (RFC examples),
`fixtures/ijson/vectors.json`, the transcribed `esNumberVectors` and
`canonVectors` in `fixtures/oracle/ijson-jcs.json`, and the differential job.

=== 3. CLI surface

Where `kyq` offers `check`/`fix`/`canon` behaviour it uses the same user-visible
contract as `ijson-jcs`, for JSON *and* for KYAML inputs:

* `check` prints `OK path`, `NOT CANONICAL path` or `INVALID path: reason`, one
  line per file on stdout. Exit 0 if every file canonical, 1 if some valid but
  not canonical (none invalid), 2 if any invalid or unreadable.
* `fix` rewrites each valid, non-canonical file to canonical form plus a single
  `\n`; prints `OK path` when it is already byte-identical (and does not write),
  `FIXED path` otherwise; `INVALID` files are left untouched and the other files
  are still processed. Exit 0 if every file was valid, else 2.
* `canon` reads stdin, writes the canonical form to stdout with *no* trailing
  newline (the bytes to hash/sign), errors to stderr as
  `INVALID <stdin>: reason`, exit 2 on invalid.
* `--` before file names beginning with `-`; a usage error exits 2.

Executable: `conformance/test/cli.test.js`, including the CLI cases transcribed
from `ijson-jcs`'s own `tests/cli.rs`.

=== 4. The trailing-newline rule (load-bearing)

[cols="1,3",options="header"]
|===
| Form | Bytes on disk

| JCS canonical bytes (hash/sign input)
| `b` — exactly `to_jcs(&value)`, no trailing newline.
| On-disk JSON file considered canonical by `check`
| `b` *or* `b ++ "\n"`; anything else (`b ++ "\n\n"`, `b ++ "\r\n"`, trailing
  space, leading whitespace) is `NOT CANONICAL`.
| `fix` output
| Always `b ++ "\n"`.
| `canon` output
| Always `b` (no newline).
|===

KYAML uses the same rule around the formatter's single trailing newline: the
canonical text is accepted with or without that final newline, and `fix` always
writes it.

Executable: `fixtures/ijson/check.json` (13 file-level vectors) and
`cli.test.js`; both directions of the rule are pinned, not just the happy path.

== KYAML → JCS pipeline (how kyq bridges the two)

----
YAML (KYAML) ──parse (kyaml)──▶ AST ──φ──▶ JSON value
                                            │
                                      validate (strict)
                                            │
                                            ▼
                                     to_jcs(bytes) / to_jcs_string
----

* Step 1 — `parse`: KYAML parser per `docs/KYAML_SPEC.adoc`. Rejects duplicate
  keys, complex/merge keys, alias cycles, unsupported tags, non-string mapping
  keys (at the bridge), surrogates and noncharacters.
* Step 2 — φ: `null`→`null`; `bool`→boolean; `int`→JSON number after a `BigInt`
  range check; `float`→JSON number after a finiteness check; `string`→JSON
  string after the Unicode checks; `seq`→array; `map` (string keys)→object.
  Lossy cases are refused, never coerced (`docs/KYAML_SPEC.adoc` §6).
* Step 3 — `to_jcs`: the same canonicaliser for both formats. There is no second
  implementation in the gate; the Rust crate remains the external oracle.

The gate implements this pipeline once, in `conformance/src/`:
`kyaml.js` (parser) → `bridge.js` (φ) → `json.js` + `jcs.js` (validation and
canonical bytes) → `cli.js` (the CLI contract above).

== Known upstream interaction: JCS text of a large float is not strict input

`ijson-jcs` refuses an *integer token* outside ±(2^53−1) but accepts any float
token. JCS then prints a float with ES number rules, which for values such as
`1e20` yields an integer-looking token:

[source,text]
----
input       1e20                      (valid I-JSON: float token)
canon      100000000000000000000      (JCS bytes; correct per RFC 8785 §3.2.2.3)
re-parse   INVALID: Number outside safe integer range
----

So `ijson-jcs canon` (and `kyq-conformance canon`) succeeds while re-reading the
resulting bytes strictly does not. `ijson-jcs fix` has the same round-trip gap:
it will write such a file, and `check` will then call it `INVALID`.

`kyq` **does not invent a second canonical form to paper over this.** Byte
equality with the oracle is the contract, so the gate reproduces the behaviour
and pins it:

* `fixtures/ijson/vectors.json` marks these two vectors `"reflexive": false`;
* `conformance/test/json.test.js` has a dedicated test named
  "known upstream interaction", asserting both the bytes and the refusal;
* practical guidance: hash `canon` output (do not re-read it), or keep
  magnitudes that large as strings. A future `ijson-jcs` revision that accepts
  an integer token when its value came from a float token would remove the gap;
  until then the gate reports exactly what the oracle reports.

(This is a finding from building the gate, not a kyq defect. It is also the
reason `docs/CONFORMANCE_GATE.adoc` says the gate makes byte-compatibility
*testable*, not that the oracle is bug-free.)

== What "guaranteed" means for this document

* Byte equality with `ijson-jcs` on the shared corpus (valid, duplicate-key,
  unsafe-integer, surrogate/noncharacter, canonical-bytes and CLI vectors) —
  transcribed statically, and re-derived in CI by building the pinned commit.
* `check`/`fix`/`canon` exit codes and printed lines match `ijson-jcs` for JSON
  inputs; for KYAML inputs the pipeline above is applied first, then the same
  rules and the same exit codes.
* No bypass: a YAML input with a duplicate key that JSON would collapse is still
  `INVALID`, because the check happens at the YAML parse layer.
* Errors are typed (`code`, `line`, `column`, `path`, `kind`) with a text and a
  JSON rendering; no invalid input is classified valid.

Not claimed: that `ijson-jcs` is itself bug-free (see above), that the
AffineScript implementation under `src/` satisfies this contract (it does not
compile yet), or that any of this is formally proved.

== The gate and the AffineScript-only invariant

`coordination.k9` requires implementation code to be AffineScript. The gate in
`conformance/` is a *verification harness*, not the kyq implementation: it is
plain ESM JavaScript with no dependencies, in the same spirit and the same role
as `scripts/check-action-pinning.js` and the other repo-owned tooling under
`scripts/`. It exists so the contracts in this document can be executed at all,
since `src/*.affine` does not compile under AffineScript 0.1.1
(`docs/status/A1_GRAMMAR_CENSUS.adoc`).

Two rules keep that honest:

. the gate MUST NOT be presented as kyq's implementation in release notes,
  README claims or the deed; it is the oracle the implementation must pass;
. when the AffineScript implementation builds, it MUST pass the same corpus, and
  the differential test then compares three implementations (Rust oracle,
  JS gate, AffineScript kyq) rather than substituting one for another.
