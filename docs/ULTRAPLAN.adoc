= kyq v0.2 Ultraplan — From Scaffold to Guaranteed KYAML + JCS Canonicalisation
:toc: macro
:toclevels: 3
:icons: font
:revdate: 2026-10-23
:author: Agent (Arena) + hyperpolymath

Abstract: a field-ready plan to take `metadatastician/kyq` from an honest
scaffold (Phase 0: 5% milestones, build does not parse) to a tool that
*guarantees* it works for KYAML (Kubernetes YAML, a well-defined YAML 1.2
subset) and for the estate JSON canonical form defined by
`hyperpolymath/ijson-jcs` (I-JSON RFC 7493 + JCS RFC 8785). The plan is
ordered by hard dependency: first the repository must be truthful, green in
CI, documented and secure; then KYAML must be proved working; then the JCS
canonical pipeline must be proved working on top of KYAML. Mathematical proofs
are catalogued, not discharged, in this document.

toc::[]

== How to read this document

* *Honest* means no placeholder binary, no fake test pass. The `Justfile`
  recettes `build`, `test`, `bench`, `wasm` currently fail with
  `not implemented: AffineScript 0.1.1 does not parse src/`. That is load-bearing.
* *Guaranteed works for KYAML* means: for every input in the defined KYAML
  language, `kyq` either accepts it and produces the specified output, or
  rejects it with a structured, locatable error; no silent mis-parse; no crash;
  behaviour is specified by an executable grammar, covered by property tests,
  and bounded by stated resource limits.
* *Guaranteed works for JCS* means the same, plus byte-for-byte determinism
  per RFC 8785, via the `ijson-jcs` contract (`check`/`fix`/`canon` semantics,
  trailing-newline rule, failure modes).
* The companion catalogue `docs/PROOF_OBLIGATIONS.adoc` lists the theorems
  that the finished product must satisfy. This ultraplan does *not* prove them;
  it sequences the work so proofs can be added without rework.

=== 0.4 What "kyaml" means today

* `coordination.k9` describes kyq as *an AffineScript-based KYAML processor
  intended as a smaller, K8s-aware alternative to yq* with target formats
  `YAML`, `JSON`, `K8s manifests`, YAML versions `YAML 1.2`, and K8s target
  `v1.25 → v1.30`. No formal KYAML grammar artifact exists. The intended
  meaning is *the subset of YAML 1.2 that Kubernetes actually emits and
  accepts*, plus K8s conventions (multi-doc `---`, anchors/aliases used
  sparingly, tags rare, `apiVersion`/`kind`/`metadata`/`spec` required shapes).
* Lint rules in `RequiredFields.affine` cover `required-field` for Pod,
  Deployment, Service, ConfigMap, Secret; `README.md` enumerates a broader rule
  set (`deprecated-api`, `latest-tag`, `selector-mismatch`, `resource-names`,
  `label-keys`, `type-check`, etc.) that does not yet exist as code.

=== 0.5 What "ijson-jcs canonical" means

* `hyperpolymath/ijson-jcs` is the estate JSON standard (D306): I-JSON
  validation (RFC 7493 MUST + SHOULD) plus JCS canonicalisation (RFC 8785),
  Rust crate + `ijson-jcs` CLI (`check`/`fix`/`canon`), with stated exit codes,
  trailing-newline rule (*canonical bytes optionally followed by exactly one
  `\\n` are accepted by `check`; `fix` always writes canon + `\\n`; `canon`
  writes canon with no trailing newline*), duplicate-key detection at parse
  time, IEEE-754 and safe-integer `±(2^53−1)` enforcement, UTF-16 code-unit key
  sorting, and denial of unpaired surrogates / noncharacters. The crate's test
  suite (33+ cases) is the executable spec.

== 1. Mathematical proof obligations (catalogue only)

The catalogue lives in `docs/PROOF_OBLIGATIONS.adoc`. Summary below; no proofs
are attempted here.

* *KYAML language*: totality + determinism of lex/parse; bijection between
  token streams and ASTs modulo insignificant whitespace/comments; YAML 1.2 core
  schema faithfulness for the KYAML subset; multi-document equivalence;
  anchor/alias resolution termination + referential transparency; tag handling.
* *K8s schema*: soundness of `required-fields` and type rules w.r.t. the
  embedded OpenAPI schemas (`apps/v1`, `v1`, `networking.k8s.io/v1`,
  `batch/v1`, etc.); completeness bounds; `deprecated-api` rule correctly
  tracks `v1beta1`→`v1` transitions; selector-mismatch detection is sound (no
  false negatives for the checked kinds).
* *Query + mutation language*: path query semantics (`a.b`, `[0]`, `[]`,
  quoted keys) are deterministic and total on well-formed docs; `get`/`set`/`del`
  preserve document well-formedness and K8s invariants where claimed; idempotence
  of `fmt`.
* *KYAML↔JSON bridge*: `to-json`/`from-json` are semantics-preserving on the
  intersection of the two languages; lossy cases are characterised and rejected.
* *JCS/I-JSON*: parsing rejects duplicate keys before `Value` construction;
  safe-integer and float canonicalisation exactly match `ijson-jcs`
  (`serde_json` with `float_roundtrip`, ES `JSON.stringify` number rules);
  UTF-16 sort is a total order matching RFC 8785; `to_jcs` is deterministic,
  idempotent, and injective on equivalence classes of JSON values modulo key
  order/whitespace; trailing-newline rule is exactly as specified; error types
  are exhaustive.
* *Cross-cutting*: a K8s manifest round-trips `YAML → Value → JCS bytes →
  Value → YAML` without semantic change outside declared normalisations;
  resource limits and error handling are proven not to mask invalid inputs.

== 2. Sequencing principle: Working → Canonical → Proven

You cannot prove a tool correct before the tool exists, and you cannot claim
the canonical form works before the underlying YAML works. The ultraplan is
therefore strictly ordered:

[horizontal]
Phase 0 (now) :: Make the repository honest and green
Phase 1 (next) :: Guarantee KYAML works (parse/lint/query/fmt, no JCS yet)
Phase 2 (after) :: Guarantee JCS canonical works *on top of* Phase 1
Phase 3 (then)  :: Discharge proof obligations, carrying evidence in-repo
Phase 4 (last)  :: Estate adoption (dogfood, docs site, editor tooling)

Each phase has a *gate* that must pass before the next phase starts. No phase
is allowed to produce a placeholder artefact that earlier phases pretend is real.

== 4. Phase 1 — Guarantee KYAML works

Gate to exit Phase 1: a `kyq` binary can be built on a clean checkout,
`kyq lint`/`fmt`/`get`/`set`/`del`/`validate`/`split`/`merge`/`diff`/`to-json`/`from-json`
exist and are specified, and a property suite proves the parser total/deterministic
on the defined KYAML language (see proof catalogue Thms 1–6). CI runs build + unit +
integration + fixtures on every PR.

=== 4.1 Define KYAML precisely

Create `docs/KYAML_SPEC.adoc` as the normative subset:

* Base: YAML 1.2 "Core Schema" + Kubernetes conventions; explicit `---` multi-doc,
  anchors/aliases allowed, tags allowed but not required, directives optional.
* Exclusions: YAML 1.2 features K8s never emits (e.g. `!!timestamp` implicit,
  complex keys) are either rejected or normalised — the spec must say which.
* Fixtures become spec: `examples/deployment.yaml` (good) and
  `tests/fixtures/invalid-deployment.yaml` (bad) plus
  `docs/KYAML_SPEC.adoc#examples` are the first conformance tests.

=== 4.2 Choose an implementation path (decision required)

There are three honest ways to clear AffineScript blocker 1. Phase 1 needs one:

[cols="2,3,2",options="header"]
|===
| Path | What changes | Cost

| A — AffineScript port (purist)
| Rewrite ~50% of `src/` to AffineScript 0.1.1 grammar (mechanical 5% +
  semi-mechanical 25% + AST rewrite) and add stdin/argv support (blocker 3) in
  the AffineScript toolchain itself.
| Preserves `affinescript-only` with no dispensation; longest calendar time;
  depends on upstream.

| B — Rust bootstrap with AffineScript shim (pragmatic)
| Add a `Cargo.toml` and a `crates/kyq-cli` binary in Rust that implements the
  KYAML spec on top of a YAML 1.2 crate (`yaml-rust2`/`serde_yaml` verified
  against the KYAML fixtures); keep `src/*.affine` as the normative spec and
  generate or hand-port it; Justfile dispatches `just build` → `cargo build`
  when `affinescript` is absent.
| Requires a one-paragraph dispensation in `coordination.k9`
  (`invariants: {rule: affinescript-only, waived-until: <date>, reason: …}`);
  fastest to working; aligns naturally with `ijson-jcs` (Rust) in Phase 2.

| C — Hosted AffineScript (hybrid)
| Compile AffineScript to WASM via `affinescript compile` for the pure parser
  and drive I/O from a tiny Rust host that supplies argv/stdin (fixing blocker 3
  at the host layer, not the compiler).
| Keeps most code in AffineScript; needs a working `affinescript compile`
  today (not yet true) so still blocked on Path A for parsing.

|===

Recommendation: Path B, with Path A tracked as the convergence goal.
Rationale: (i) `ijson-jcs` is already Rust, so Phase 2 integration is a Cargo
dependency, not a cross-language FFI; (ii) property tests + fixtures can be
written once and reused for Path A later; (iii) the dispensational language in
`coordination.k9` keeps the estate rule visible rather than silently violated.
If the owner prefers strictness, Path A is viable but the roadmap durations
shift by +2–4 weeks.

== 5. Phase 2 — Guarantee JCS canonical works (on top of KYAML)

Gate to exit Phase 2: `kyq` speaks the same canonical contract as
`ijson-jcs check`/`fix`/`canon` on the intersection of the two input languages,
with byte-equal output for the same logical JSON value, and the same exit-code
and error taxonomy. The integration is proven not to reintroduce duplicate-key
or noncharacter bypasses.

=== 5.1 The canonical pipeline

----
YAML (KYAML) ──parse──▶ Value (lossless) ──validate I-JSON──▶ JCS bytes
        │                                           │
        │ to-json (stable)                    to_jcs / to_jcs_string
        ▼                                           ▼
     JSON text  ◀── from-json ──  Value  ── check/fix/canon ── bytes on disk
----

* KYAML `to-json` must emit JSON that `ijson-jcs` would accept in
  `JsonMode::Strict`; if it does not, the pipeline must error, not silently
  coerce.
* For hashing/signing, the hash input is *exactly* `to_jcs(&value)` (no trailing
  newline). For on-disk files, `fix` semantics apply (canon + single `\\n`).
  Both rules are already specified by `ijson-jcs`; kyq must not invent a
  second trailing-newline policy.
* Duplicate keys, unsafe integers, floats outside IEEE-754, lone surrogates,
  noncharacters must be caught at the YAML→Value boundary, not only at the
  Value→bytes boundary — otherwise `serde_yaml`/`serde_json` collapsing would
  hide them (the `validate_i_json` vs `parse_json` caveat in `ijson-jcs` docs).

=== 5.2 Implementation (Path B)

* `Cargo.toml` adds `ijson-jcs = { git = "https://github.com/hyperpolymath/ijson-jcs", … }`
  (or a version once it publishes). The `kyq` crate exposes:

  * `kyq::kyaml::parse(&str) -> Result<Document>`
  * `kyq::kyaml::to_value(&Document) -> serde_json::Value` (lossless, typed)
  * `kyq::canon::canonical_bytes(&Value) -> Result<Vec<u8>>` (delegates to `ijson_jcs::to_jcs`)
  * CLI subcommands `kyq canon`, `kyq check`, `kyq fix` that mirror `ijson-jcs`
    exit codes (0/1/2) for JSON-file inputs, and extend them to YAML inputs via
    the pipeline above.

* CLI help must state the trailing-newline rule verbatim, as `ijson-jcs` does.

=== 5.3 Testing strategy (maps 1:1 to proof obligations Thms 7–12)

* Unit: every example in `ijson-jcs` README becomes a kyq test case.
* Property: `canon(canon(x)) == canon(x)` (idempotence); `canon(x) == canon(y)`
  iff `x` and `y` are the same JSON value modulo key order/whitespace;
  UTF-16 sort is total and stable; number serialisation matches `ijson-jcs`
  fixtures (including `-0`, `1e21`, subnormals).
* Integration: `kyq check`/`fix`/`canon` produce byte-equal output to
  `ijson-jcs check`/`fix`/`canon` on a shared corpus; `diff` on the two
  binaries must be empty.
* Negative: duplicate-key YAML (e.g. `a: 1\na: 2`) is rejected before JCS;
  documents with noncharacters/unpaired surrogates are rejected with locations.

== 6. Phase 3 — Proof foundations

Gate to exit Phase 3: each theorem in `docs/PROOF_OBLIGATIONS.adoc` is either
mechanically proven (Lean/Coq/TLA+ artifact in `proofs/`) or has a tracked
property-test suite + manual proof sketch that the owner has signed. No theorem
is both unproven and un-tracked.

This phase is intentionally *after* working code: proofs are written against
the executable spec and the real fixtures, not against a wish.

Outline (not proofs):

* `proofs/kyaml/` — YAML 1.2 subset grammar, lex/parse totality, anchor termination.
* `proofs/jcs/` — UTF-16 sort total order, ES number serialisation correctness,
  canonical bytes determinism + injectivity, trailing-newline handling.
* `proofs/estate/` — K8s schema soundness, selector-mismatch soundness,
  resource-name/label-key validation.
* Tooling choice (Lean 4 vs Coq vs TLA+) is deferred; the first proof should be
  `JCS idempotence`, the smallest closed property with independent value.
